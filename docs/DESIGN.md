# Alvik Match Control v2 ระบบออกแบบ

เอกสารนี้เขียนให้โมเดลหรือคนที่จะลงมือสร้างอ่านแล้วทำต่อได้เลย ทุกส่วนที่ระบุว่า "ต้อง" เป็นข้อบังคับ ส่วนที่ระบุว่า "แนะนำ" ปรับได้

สถานะ สร้างจริงแล้ว (ดูหัวข้อ "สิ่งที่สร้างจริงต่างจากแบบ" ด้านล่าง) ข้อ 16 ใช้ค่าที่ออกแบบไว้ก่อนทั้งหมด

## สิ่งที่สร้างจริงต่างจากแบบ

ลำดับความสำคัญ เมื่อเอกสารส่วนอื่นขัดกับหัวข้อนี้ ให้ถือหัวข้อนี้เป็นหลัก

| เรื่อง | ในแบบ | ที่สร้างจริง |
|---|---|---|
| เครื่องมือ | Svelte, Vite, Vitest, pnpm | HTML กับ JavaScript ธรรมดา (ES modules) ไม่ต้อง build เสิร์ฟจาก GitHub Pages ได้เลย |
| ตัวตัดสินผลเกม | `packages/core` แล้วทดสอบเทียบกับ SQL | ตัดสินที่ฐานข้อมูลที่เดียว (`a2_decide`) หน้าเว็บมี `previewDecide` ไว้แสดงล่วงหน้าเท่านั้น |
| งานหลายรายการ | หลาย event | event เดียว (`a2_event` id=1) |
| การยืนยันตัวตน | Supabase Auth | รหัสผ่านแอดมินกับ PIN กรรมการ เก็บแบบ hash ใน `a2_secret` ทุกคำสั่งเขียนต้องส่งรหัสมาด้วย |
| ตั้งรหัสครั้งแรก | ไม่มี | `a2_setup` เรียกได้ครั้งเดียวตอนยังไม่มีรหัส ใครเปิด `/admin/` ก่อนเป็นคนตั้ง ให้ผู้จัดเปิดก่อนแจกลิงก์ |
| ตาราง | ชื่อ `alvik_*` ต่อยอด | ตารางใหม่ขึ้นต้น `a2_` v1 (`alvik_rooms`, `alvik_keys`) คงไว้ |
| หมด Setup | เริ่มเกมต่ออัตโนมัติ | หยุดที่ 0:00 รอกรรมการหรือแอดมินกดเริ่มจับเวลาแข่ง |
| ส่งออก | Excel | JSON (ปุ่มในหน้าตั้งค่า) |
| กรรมการหลุดเน็ต | คิวออฟไลน์ ส่งซ้ำ | ยังไม่ได้ทำ ถ้าหลุดจะแสดงสถานะหลุดและกดไม่ได้จนกว่าจะต่อเน็ตใหม่ |

### ตั้งเวลาเปิดคิว (เพิ่มภายหลัง)

- คอลัมน์ใหม่ใน `a2_match` คือ `sched_at` (เวลา) `sched_field` (สนาม) `auto_open` (เปิดเองหรือไม่)
- แอดมินตั้งในแท็บ "ตั้งเวลา" มีปุ่มเติมอัตโนมัติจากเวลาคู่แรก ระยะห่างต่อรอบ และจำนวนสนาม แก้รายคู่ได้ แล้วบันทึกผ่าน `a2_adm_schedule`
- `a2_tick()` เรียกจากทุกหน้าทุก 8 วินาที ทำสองอย่าง คือหมดเวลานาฬิกาตามจริง และเปิดคิวให้คู่ที่ `auto_open` ถึงเวลาแล้ว
- เงื่อนไขเปิดเอง คู่ต้องสถานะ `ready` (รู้ผู้เล่นครบ) สนามที่ระบุต้องว่าง หรือคู่เดิมในสนามจบแล้ว ถ้าไม่ครบจะไม่เปิดและรอรอบ tick ถัดไป
- แอดมินกดเปิดก่อนเวลาได้เสมอ หน้า ref และ TV แสดงเวลานัดของคู่ถัดไป

## โครงโค้ดที่ได้

## 1. เป้าหมาย

ระบบจัดการแข่งขัน Arduino Alvik Smart Logistics Challenge (9 ทีม) แยกเป็น 3 เว็บที่ใช้งานคนละคน

| เว็บ | คนใช้ | อุปกรณ์ | หน้าที่ |
|---|---|---|---|
| Admin | ผู้จัด 1 ถึง 2 คน | โน้ตบุ๊ก | จัดการและแก้ได้ทุกอย่าง เปิดคิวให้แต่ละสนาม |
| TV | ไม่มีคนกด | จอทีวีหรือโปรเจกเตอร์ 16:9 | แสดงสาย ตารางคะแนน นาฬิกา และผลสด |
| Referee | กรรมการประจำสนาม | มือถือหรือ iPad | กดคะแนนของคู่ที่แอดมินเปิดให้เท่านั้น |

หลักที่ต้องยึด
1. Realtime ทุกจอเห็นข้อมูลตรงกันภายใน 1 วินาที
2. กันพลาด กรรมการกดได้เฉพาะคู่ที่ถูกเปิดคิวในสนามของตัวเอง แก้ผลย้อนหลังไม่ได้ ต้องให้แอดมินแก้
3. ใช้ง่าย กรรมการไม่ต้องเรียนรู้ เปิดลิงก์ ใส่ PIN เลือกสนาม แล้วกดได้เลย
4. ข้อมูลจริงอยู่ที่ฐานข้อมูลที่เดียว การตัดสินผลและการเลื่อนรอบคำนวณที่ฐานข้อมูล
5. ทุกการแก้มีบันทึก ย้อนดูและย้อนกลับได้

นอกขอบเขต ระบบนี้ไม่ทำการลงทะเบียนทีม ไม่ทำระบบผู้ชม ไม่ต้องรองรับหลายรายการแข่งพร้อมกัน (แต่ schema รองรับ event_id ไว้แล้ว)

## 2. กติกาที่ระบบต้องรู้

อ้างอิง กติกาการแข่งขันหุ่นยนต์ Arduino Alvik (rule/*.pdf) และ FAQ 10-11-2026

### 2.1 เวลา
- Setup 1:00 (ข้อ 3.1)
- ภารกิจ 1:30 นับจากสัญญาณเริ่ม (ข้อ 3.2)
- ผู้จัดสุ่มแบบสนาม 1 ถึง 3 ก่อนเริ่ม Setup ทั้งสองทีมใช้แบบเดียวกัน (ข้อ 2.3) ระบบไม่สุ่มเอง ให้กรรมการเลือกแบบที่สุ่มได้
- นับเวลาจนจอดแท่นที่ 3 สำเร็จ (FAQ 33)

### 2.2 ข้อมูลต่อฝั่งต่อเกม
| field | ความหมาย |
|---|---|
| parked | จำนวนแท่นที่จอดสำเร็จ 0 ถึง 3 |
| full_ms | เวลาที่จอดครบ 3 แท่น (มีเมื่อ parked = 3) |
| lift_ms | เวลายกแท่นแรกสำเร็จ (ข้อ 5.2) |
| exit_ms | เวลาที่หุ่นออกพ้นกรอบแดงทั้งหมด (ข้อ 5.3) |

ทุกเวลาเป็นมิลลิวินาทีนับจากสัญญาณเริ่มภารกิจ แสดงผลเป็น m:ss.d

### 2.3 ลำดับการตัดสินหนึ่งเกม (ข้อ 6)
ฟังก์ชัน `decide(game)` คืนค่า `{ side: 'red'|'blue'|null, method, reason }`

1. ฝั่งเดียวจอดครบ 3 ชนะ method `full` (6.1)
2. จอดครบทั้งคู่ เวลาน้อยกว่าชนะ method `full` (6.1)
3. ไม่มีใครครบ จำนวนแท่นมากกว่าชนะ method `count` (6.2)
4. เท่ากัน ยกแท่นแรกได้ฝั่งเดียวชนะ หรือยกเร็วกว่าชนะ method `lift` (6.3)
5. ไม่มีใครยกได้ ออกจากกรอบแดงได้ฝั่งเดียวชนะ หรือออกเร็วกว่าชนะ method `exit` (6.4)
6. ยังไม่ได้ผล
   - ไม่มีฝั่งไหนออกจากกรอบแดงเลย ผลคือ `judge` กรรมการตัดสิน (FAQ 35)
   - กรณีอื่นที่เท่ากันทุกอย่าง ผลคือ `replay` แข่งใหม่ทันทีด้วยแบบสนามเดิม (FAQ 34)

ต้องมี unit test ครอบตัวอย่างทั้ง 6 แถวในตารางตัวอย่างของกติกา และกรณี FAQ 33 34 35

### 2.4 รูปแบบการแข่ง
| รอบ | สาย | ทีม | ผ่าน |
|---|---|---|---|
| รอบแรก | A | ลำดับ 1 2 3 | ที่ 1 และ 2 |
| รอบแรก | B | ลำดับ 4 5 6 | ที่ 1 และ 2 |
| รอบแรก | C | ลำดับ 7 8 9 | ที่ 1 และ 2 |
| รอบสอง | D | ที่ 1 A, ที่ 1 C, ที่ 2 B | ที่ 1 |
| รอบสอง | E | ที่ 1 B, ที่ 2 A, ที่ 2 C | ที่ 1 |
| ชิงชนะเลิศ | F | ที่ 1 D กับ ที่ 1 E | แชมป์ |

- ในสายแข่งพบกันหมด 3 คู่ คู่ละ Bo3 ชิงชนะเลิศ Bo5 รวม 16 คู่
- คู่ในสาย ใช้ index ทีมในสาย [0,1] [1,2] [0,2]
- ลำดับคู่มาตรฐาน A1 B1 C1 A2 B2 C2 A3 B3 C3 D1 E1 D2 E2 D3 E3 F
- เกมที่เป็น replay ไม่นับเป็นเกมของ Bo

### 2.5 อันดับในสาย
เรียงตาม
1. จำนวนคู่ที่ชนะ
2. ผลต่างเกม (เกมชนะ ลบ เกมแพ้)
3. จำนวนเกมที่ชนะ
4. ผลคู่ที่เจอกัน (ใช้ได้เฉพาะเสมอกัน 2 ทีม)
5. แอดมินกำหนดลำดับเอง (เก็บใน `group_tiebreaks`)

ตำแหน่งในสายถือว่า "แน่นอน" เมื่อทุกคู่ในสายจบ และตำแหน่งนั้นไม่ติดเสมอที่ยังไม่ตัดสิน ทีมจะถูกส่งเข้ารอบถัดไปเมื่อแน่นอนแล้วเท่านั้น

### 2.6 อันดับรวม
| อันดับ | ทีม |
|---|---|
| 1 | ผู้ชนะ F |
| 2 | ผู้แพ้ F |
| 3= | ที่ 2 สาย D และ E |
| 5= | ที่ 3 สาย D และ E |
| 7= | ที่ 3 สาย A B C |

ค่าคงที่ของรูปแบบการแข่ง (สาย คู่ Bo การเลื่อนรอบ) เก็บใน `packages/core/format.ts` ไฟล์เดียว เผื่อเปลี่ยนรูปแบบภายหลัง

| คำ | ความหมาย | ในโค้ด |

### 4.3 แหล่งความจริง
- ข้อมูลทั้งหมดอยู่ใน Postgres
- client เขียนผ่าน RPC เท่านั้น ห้าม insert หรือ update ตารางตรง (RLS ปิดไว้)

- `packages/core` มีตรรกะเดียวกันในฝั่ง TS ไว้แสดงผลล่วงหน้า (preview) เท่านั้น ต้องมี test เทียบผลกับ SQL ด้วยชุดข้อมูลเดียวกัน

## 5. ข้อมูล (Postgres schema)

ทุกตารางมี `event_id uuid` และ `updated_at timestamptz default now()`

```sql
create table events (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  setup_ms int not null default 60000,
  game_ms int not null default 90000,
  field_count int not null default 2 check (field_count between 1 and 4),
  ref_pin_hash text,               -- sha256 ของ PIN กรรมการ
  queue_lead_ms int not null default 300000,  -- ห้องเปิดให้กรรมการก่อนเวลานัดกี่ ms (ค่าเริ่ม 5 นาที)
  tv_mode text not null default 'auto',   -- auto | groups | fields | draw | champion
  tv_focus_field int,
  draw_state jsonb,                -- สถานะแอนิเมชันจับสายที่ TV เล่น
  created_at timestamptz default now()
);

create table teams (
  id uuid primary key default gen_random_uuid(),
  event_id uuid references events on delete cascade,
  seed int not null check (seed between 1 and 9),
  name text not null default '',
  unique (event_id, seed)
);

create table matches (
  event_id uuid references events on delete cascade,
  code text not null,              -- A1 .. E3, F
  stage text not null,             -- r1 | r2 | final
  grp text,                        -- A..E หรือ null
  order_no int not null,
  bo int not null,
  red_src jsonb not null,          -- {"seed":1} หรือ {"g":"A","p":1}
  blue_src jsonb not null,
  red_team uuid references teams,  -- เติมโดย recompute()
  blue_team uuid references teams,
  status text not null default 'locked',  -- ดู state machine 7.2
```

## 6. RPC

ทุก RPC เป็น `security definer`, `set search_path = public`, ตรวจสิทธิ์ก่อนทำงาน, เขียน audit_log, เรียก `recompute(event_id)` เมื่อผลเปลี่ยน และคืน row ที่เปลี่ยนเพื่อให้ client อัปเดตทันทีโดยไม่ต้องรอ realtime

### 6.1 ระบบ
| RPC | ใคร | ทำอะไร |
|---|---|---|
| `server_now()` | ทุกคน | คืนเวลาเซิร์ฟเวอร์ ms ใช้ปรับนาฬิกา |
| `recompute(event)` | ภายใน | ตัดสินเกมที่ review ไม่ได้, นับ red_wins blue_wins, หา winner, คำนวณ standings, เติม red_team blue_team ของคู่ถัดไป, ปรับ status locked เป็น ready |

### 6.2 กรรมการ
กรรมการไม่มีบัญชี พิสูจน์ตัวด้วย `pin` + `device_id` (uuid สุ่มเก็บในเครื่อง) + `session_id` ของสนาม

| RPC | เงื่อนไข | ทำอะไร |
|---|---|---|
| `ref_login(pin, device)` | PIN ถูก | คืน event_id และรายการสนาม |
| `ref_claim(pin, device, field)` | สนามนั้นมีคิวที่ `is_open` (ถึงเวลาเปิดห้อง หรือแอดมินกดเปิดแล้ว) และยังไม่มีอุปกรณ์อื่นถือ หรืออุปกรณ์เดิมหายไปเกิน 30 วินาที | ผูกอุปกรณ์กับสนาม คืน session_id และเปลี่ยนคิวเป็น active |
| `ref_heartbeat(device, field, session)` | | อัปเดต ref_seen_at ทุก 10 วินาที |
| `ref_op(device, field, session, game_id, op, arg, op_id)` | session ตรงกับสนาม, คู่ไม่ done, เกมอยู่ในสถานะที่ op อนุญาต | แก้เกมทีละ op |
| `ref_timer(device, field, session, action)` | เหมือนข้างบน | start_setup, start_game, pause, resume, reset |
| `ref_finish_game(device, field, session, game_id, expected_version)` | เกมอยู่ live หรือ review | เปลี่ยนเป็น review แล้ว decide ถ้าได้ผลเป็น done, ถ้า replay สร้างเกมใหม่ pattern เดิม, ถ้า judge รอ `ref_judge` |
| `ref_judge(..., game_id, side)` | ผล decide เป็น judge หรือ replay | กรรมการเลือกผู้ชนะ (FAQ 35) |
| `ref_release(device, field)` | | ปล่อยสนาม |

op ที่อนุญาต
| op | arg | ผล |
|---|---|---|
| `pattern` | 1..3 | ตั้งแบบสนาม ได้เฉพาะก่อน start_game |
| `parked` | +1 / -1 | ปรับจำนวนแท่น ถ้าครบ 3 และ full_ms ว่าง ใส่ full_ms = เวลาปัจจุบันของนาฬิกาสนาม |
| `lift` | null หรือ ms | ประทับเวลายกแท่นแรก null = ใช้เวลานาฬิกา |
| `exit` | null หรือ ms | ประทับเวลาออกจากกรอบแดง |
| `clear` | ชื่อ field | ลบค่าที่ประทับผิด ได้เฉพาะระหว่างเกม live |

เวลาที่ประทับคำนวณที่เซิร์ฟเวอร์จาก `timer_ends_at` ไม่เชื่อเวลาจากเครื่องกรรมการ ยกเว้นตอน replay offline queue ที่ส่ง `client_elapsed_ms` มา ให้ใช้ค่านั้นถ้าไม่ต่างจากที่เซิร์ฟเวอร์คำนวณเกิน 3 วินาที

หลังเกม done กรรมการแก้เกมนั้นไม่ได้อีก ต้องให้แอดมินแก้

## 7. State machine

### 7.1 สนาม (fields)
```
ว่าง (slot_id null)
  กรรมการ claim คิวที่ is_open   เป็น  มีคิว timer idle (คิวเป็น active)
มีคิว timer idle
  start_setup          เป็น  setup running 1:00
setup
  หมดเวลา หรือ start_game  เป็น  game running 1:30 เกมเป็น live
game
  หมดเวลา              เป็น  over เกมเป็น review อัตโนมัติ
  จอดครบ 3 ทั้งสองฝั่ง    เป็น  over (FAQ 33)
over
  finish ได้ผล          เป็น  idle รอเกมถัดไป หรือคู่จบ
คู่จบ
  สนามยังถือคู่ไว้จนแอดมินกด "ปิดคิว" หรือ assign คู่ใหม่ (แสดง "คู่นี้จบแล้ว")
```
pause และ resume ทำได้ทุก phase ที่ running โดยเก็บ timer_left_ms

การหมดเวลาตรวจจากฝั่ง client ของสนาม (กรรมการ) แล้วเรียก `ref_timer(..., 'expire')` เซิร์ฟเวอร์ตรวจว่า now() >= timer_ends_at จริงก่อนเปลี่ยน ถ้าไม่มีกรรมการออนไลน์ หน้าแอดมินเป็นคนเรียกแทน

### 7.2 คู่ (matches)
```
locked   ยังไม่รู้ทีมครบ
ready    รู้ทีมแล้ว
live     มีเกม live หรือ review
done     มีผู้ชนะ
```
`recompute` เป็นคนเปลี่ยน locked กับ ready, เกมแรก start เปลี่ยนเป็น live, ชนะครบเปลี่ยนเป็น done

คิวมีสถานะของตัวเอง
```
planned    วางไว้แล้ว รอเวลา
(เปิดห้อง) ถึง opens_at หรือแอดมินกดเปิด และคู่ ready  ห้องกดได้
active     กรรมการ claim แล้ว
done       คู่จบ
cancelled  ยกเลิก
```
การเปิดห้องตามเวลาไม่ใช้ cron คำนวณจากเวลาเซิร์ฟเวอร์ตอนอ่านและตอนตรวจสิทธิ์ (`now() >= scheduled_at - queue_lead_ms`) ทุกเว็บที่เปิดอยู่เห็นสถานะเปลี่ยนเองจากตัวนับเวลาฝั่ง client ที่อิง offset เซิร์ฟเวอร์ และ RPC ฝั่งกรรมการตรวจซ้ำที่เซิร์ฟเวอร์เสมอ

ถ้าคิวถึงเวลาแต่คู่ยัง locked (รอผลคู่ก่อนหน้า) ห้องยังไม่เปิด หน้ากรรมการแสดง "รอผล D1 ก่อน" และเปิดเองทันทีที่คู่ ready

### 7.3 เกม (games)
```
ready   ตั้งแบบสนามได้
live    นาฬิกาเกมเดินอยู่ กดคะแนนได้
review  หมดเวลาหรือกดจบ รอยืนยัน
done    ได้ผู้ชนะ
replay  เสมอ (FAQ 34) ระบบสร้างเกมใหม่แบบสนามเดิมต่อท้าย
void    แอดมินยกเลิก
```

## 8. Realtime

### 8.1 ช่องทาง
| ช่อง | ใครฟัง | ข้อมูล |
|---|---|---|
| `postgres_changes` บน matches, games, fields, events, group_tiebreaks filter event_id | ทุกเว็บ | การเปลี่ยนข้อมูล |
| `presence` channel `event:<id>` | admin ดู, ref ส่ง | อุปกรณ์กรรมการไหนออนไลน์อยู่สนามไหน |
| `broadcast` channel `event:<id>` ข้อความ `ping` | ทุกเว็บ | ทดสอบหน่วงเวลา แสดงในหน้าแอดมิน |

### 8.2 วิธีโหลดข้อมูลบน client (ทุกเว็บใช้แบบเดียวกัน)
1. subscribe ก่อน แล้วเก็บ event ที่เข้ามาไว้ใน buffer
2. โหลด snapshot จาก view ทั้งหมด
3. apply buffer ที่ `updated_at` ใหม่กว่า snapshot
4. หลังจากนั้น apply ทีละ event
5. ถ้า channel หลุด (`CLOSED`, `CHANNEL_ERROR`, `TIMED_OUT`) แสดงสถานะ "กำลังเชื่อมใหม่" แล้วทำข้อ 1 ถึง 3 ใหม่
6. ทุก 30 วินาที โหลด snapshot ซ้ำเงียบๆ กันข้อมูลตกหล่น

store เก็บเป็น Map ตาม primary key ข้อมูลที่คำนวณได้ (standings, ranking) ไม่ต้องคำนวณเอง อ่านจาก view แต่ preview ระหว่างกดใช้ `packages/core`

### 8.3 นาฬิกา
- ตอนเปิดเว็บเรียก `server_now()` 5 ครั้ง ใช้ค่าที่ round trip สั้นสุด `offset = server - (t0 + t1) / 2`
- เวลาที่เหลือ `left = timer_ends_at - (Date.now() + offset)`
- วาดด้วย requestAnimationFrame ไม่ต้องส่ง tick ผ่านเครือข่าย
- ทุกจอจึงเดินตรงกันภายในราว 100 ms
- เสียงสัญญาณเริ่มและหมดเวลาเล่นที่จอ TV และเครื่องกรรมการ (ปิดได้)

### 8.4 offline ของกรรมการ
- ถ้าเน็ตหลุด op ถูกเก็บใน IndexedDB พร้อม op_id และ client_elapsed_ms
- UI ยังกดได้ แสดงค่าแบบ optimistic และแถบสีเหลือง "ยังไม่ส่ง 3 รายการ"
- เมื่อกลับมาออนไลน์ส่งตามลำดับ ถ้ามี error `stale` หรือ `forbidden` หยุดคิวแล้วแสดงให้กรรมการรู้
- ปุ่ม "จบเกม" กดไม่ได้ระหว่างที่ยังมี op ค้างส่ง

### 9.3 ระหว่างแข่ง (วนต่อคู่)
0. ตอนเตรียมงาน แอดมินกด "สร้างตารางเวลา" ใส่เวลาเริ่มแข่ง (เช่น 13:00) และเวลาต่อคู่ (เช่น 10 นาที) ระบบวางคิวครบ 16 คู่ลงสนามพร้อมเวลานัด แล้วปรับรายคิวได้
1. หน้าแอดมิน แท็บ คิว เห็นตารางเวลาแยกตามสนาม ใกล้ถึงเวลาคิวไหน คิวนั้นเด่นขึ้น มีตัวนับถอยหลัง
2. คิวที่ตั้งโหมด auto ห้องเปิดเองก่อนเวลานัด 5 นาที (ปรับได้) หรือแอดมินกด "เปิดห้องตอนนี้" เพื่อเปิดก่อนเวลา และถ้างานช้ากว่าแผน กด "เลื่อนที่เหลือ +10 นาที"
3. เครื่องกรรมการที่หน้าเลือกสนาม เห็นสนามที่ห้องเปิดสว่างขึ้นพร้อมชื่อคู่ ส่วนสนามที่ยังไม่เปิดแสดง "คู่ถัดไป A2 เวลา 13:20 เปิดห้อง 13:15" แตะไม่ได้
4. กรรมการแตะสนาม 1 เข้าหน้ากดคะแนน
5. ผู้จัดสุ่มแบบสนาม กรรมการแตะ แบบ 1 2 หรือ 3
6. กรรมการกด "เริ่ม Setup" นาฬิกา 1:00 เดินบนทุกจอ
7. กด "เริ่มเกม" (หรือ Setup หมดเวลา) นาฬิกา 1:30 เดิน
8. ระหว่างเกมกด +1 แท่น, ยกแท่นแรก, ออกกรอบแดง แยกฝั่งแดงและน้ำเงิน ทีวีขึ้นทันที
9. หมดเวลาหรือจอดครบ ระบบขึ้นหน้าสรุป "แดงชนะ จอดได้มากกว่า (6.2)" กรรมการกด "ยืนยันผล"
10. ถ้าเสมอ หน้าสรุปบอก "แข่งใหม่ แบบสนาม 2" หรือ "กรรมการตัดสิน" ตามกรณี
11. วนเกมถัดไปจนคู่จบ หน้ากรรมการขึ้น "จบคู่ A1 รอคิวถัดไป" และล็อก
12. ระบบเลื่อนทีม อัปเดตตารางสายบนทีวี แอดมินเปิดคิวคู่ถัดไป
